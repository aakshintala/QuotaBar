## First-party hook contract

The current official [Claude Code Hooks reference](https://code.claude.com/docs/en/hooks) says that command-hook JSON arrives on stdin and HTTP-hook JSON arrives as the POST body. In the [common input fields](https://code.claude.com/docs/en/hooks#common-input-fields), `session_id` is described as “Current session identifier”; the docs impose no UUID syntax. The examples use `abc123`. `UserPromptSubmit` specifically receives `prompt` containing submitted text, and the docs note pasted content may be expanded inline. Thus hook bodies include user text/metadata and are not safely assumed to fit the daemon's 1 KiB normal/control request cap. The same docs say HTTP hooks POST input to the configured URL and use the JSON output format; `hookSpecificOutput.additionalContext` is the context field. `SessionStart` supports command hooks, not HTTP hooks, while `UserPromptSubmit` accepts HTTP; the repository's README command/curl for SessionStart and HTTP hook for prompt are consistent with this distinction. Claude's general `additionalContext` string cap is 10,000 characters, independent of request body size.

Official hook HTTP fields and input rules are documented at the cited reference's [HTTP hook fields](https://code.claude.com/docs/en/hooks#http-hook-fields), [common input fields](https://code.claude.com/docs/en/hooks#common-input-fields), [SessionStart input](https://code.claude.com/docs/en/hooks#sessionstart-input), and [UserPromptSubmit input](https://code.claude.com/docs/en/hooks#userpromptsubmit-input). These are first-party, live docs fetched with bounded unauthenticated GET; no quota endpoint was contacted.

## Hook body bounds, timing, and privacy

**Observed:** Swift `QuotaHTTPRequestHandler.maxRequestBytes` is 1,048,576 bytes for all requests; `QuotaHTTPServer` reads up to 65,536 bytes per receive. Swift hook handlers parse only `session_id`, and produce the existing `{}` or `hookSpecificOutput` envelope. The code comment explicitly recognizes that hook bodies can carry prompts. Current Swift `QuotaHooks` is cache-only, but is not bounded: its session map uses `""` for missing/malformed IDs and never evicts. The accepted Rust listener instead has one global 1 KiB body cap, 16 KiB header cap, 32-connection/16-handler bounds and a five-second total request-acceptance deadline; GET refresh waits 4.5 seconds. The roadmap/feed contract set SessionStart's shared refresh wait to 1.5 seconds and its route response to 2 seconds, with prompt cache-only and also at most 2 seconds.

**Recommendation for the implementer/main to rule on:** retain the global 1 KiB cap for ordinary/control routes, but dispatch hook bodies under a separate finite hook-only cap. A starting bound such as 256 KiB is generous relative to the required parsed metadata and still materially bounds memory; it is not a Claude-documented maximum and must be validated against representative *synthetic* envelope sizes, not captured prompt bodies. Reject over-cap with a safe 413. Do not keep, log, echo, or persist raw bytes/prompt; parse only bounded JSON fields needed for session identity and ignore the prompt. Implement this as a route-specific limit within the existing Axum stack, not a handwritten HTTP parser or new framework. Preserve exact loopback `Host` checking, any-Origin rejection, and control-token checks unchanged.

Timing must start at connection acceptance, not after headers: setting a two-second route timer only after parsing lets slow headers consume the current five-second allowance and defeats the hook contract. A coherent option is a two-second total deadline from accept for hook routes (and retain the listener's existing five-second bound for other routes), with a bounded header-read deadline no greater than that total. The installed SessionStart curl has a 2-second timeout and Claude command hook timeout 3 seconds; prompt's installed HTTP timeout is 2 seconds. SessionStart's provider wait remains 1.5 seconds, leaving at most 0.5 seconds for parsing/formatting/response. Prompt must not wait on refresh. Keep these budgets finite and test them from connection acceptance; this is a recommendation, not a ruling to increase any budget.

## Session identity and worsening history

**Observed contract:** feed v1 requires history by `(provider id, bucket key)`, start baseline on SessionStart, compare severity only, report only worsening buckets on prompt, expire idle sessions at 24 hours, cap at 1,024 sessions with LRU eviction, and do not update/share history for missing or malformed IDs. `unknown` is not a bucket severity; severity progression is the existing four-level healthy/warning/critical/depleted ordering. Current Swift session-start records statuses it actually recognizes, and prompt compares current statuses against a default `.healthy`; it updates the session state even when there is no alert. Therefore newly appearing severe buckets on first prompt are treated as worsening from healthy, while absent buckets are not explicitly removed from stored history. SessionStart overwrites the session's whole status baseline, so a later SessionStart can reset the baseline.

The official docs only call `session_id` a session identifier; they do not promise a UUID format. Avoid UUID-only validation. Recommend a bounded nonempty string with no control characters (and a finite byte/character maximum, e.g. 256 UTF-8 bytes) as an opaque key. Do not normalize it, log it, or treat it as a path. The exact maximum is an implementation safety bound, not a Claude guarantee. No maintenance timer is needed: expire idle entries when handling a hook, and use access/update timestamps for LRU eviction.

**Minimal ambiguity to settle before coding:** confirm whether an unreported/missing bucket should be removed from the per-session comparison map or left as the last reported status, and whether SessionStart replacement resets that session's history. Current behavior supports “replace baseline at start; prompt stores current recognized statuses,” but the normative instruction “reports only worsening bucket severity” does not fully define disappearance/reappearance. Recommend a straightforward map of current bucket severities, replacing it after each valid prompt and at SessionStart, which avoids stale removed buckets and preserves the explicit no-repeat-startup baseline. Do not turn unknown/missing into healthy, compare provider-level status, or repeat the baseline's already-reported warnings. Main owns this ruling.

## Formatter and feed boundary

The roadmap says SessionStart and CLI use the same formatter. The installed shell command currently fetches `GET /quotas`; with `--json`, it prints raw response JSON, otherwise `jq` formats a human summary. Pi also calls that same GET route. There is no existing CLI formatter contract/code to reuse. Keeping `jq` formatting in the external shell while Rust formats SessionStart would duplicate behavior and contradict the shared-formatter direction. A minimal candidate for main's decision is one `quotabard` binary with a standard-library-parsed `quota [--json|enable ID|disable ID]` subcommand: read-only `quota` fetches the same `GET /quotas`, outputs JSON for `--json`, and uses the same Rust formatter for human output and SessionStart. Enable/disable use existing authenticated control route; no probes in the CLI, new endpoint, second binary, CLI framework, or alternate cached GET route. Replace the installed shell script with a tiny wrapper only at approved cutover, preserving `QUOTA_FEED` and `--json`. The current plan's control API is PUT `/providers/{id}/enabled`; the roadmap's human CLI naming remains compatible with this candidate.

This is a recommendation, not approved consumer behavior. One unresolved detail is how a Rust subcommand is invoked from the executable staged at `~/.local/bin/quotabard` / the macOS app-support path while preserving the old shell entry point and custom `QUOTA_FEED`; keep this simple and test it in a private copy before activation.

The checked-in Swift `QuotaFeedDTO` is not the v1 Rust DTO: it lacks `schemaVersion`, `freshness`, `errorCode`, and uses legacy `unavailable`/`throttledUntil`; its `Codable` structs require their modeled fields. Do not assume serde-deserializing the Rust DTO into these exact Swift types will work. Keep client-side parsing narrowly owned: either decode a minimal Rust-owned summary representation for the formatter or derive only the necessary fields from v1 feed JSON. Avoid a generic compatibility layer. Feed v1 already defines the authoritative DTO and should not be changed just to fit old Swift structures.

Control CLI credential boundary: the daemon's runtime state is protected by its exclusive instance lock, so the CLI must not open that state as a competing writer merely to get the control token. A minimal shared read-only token loader is needed. It should safely read only the token file without following symlinks, enforce the specified format and private permissions, and never expose it in Debug/logs/URLs. For custom `QUOTA_FEED`, validate the full URL as HTTP loopback (`127.0.0.1` or `localhost`, expected configured port as applicable) before reading/sending the control token; do not permit a custom non-loopback URL to exfiltrate it. Read-only GET may preserve custom URL behavior if safely constrained, but do not attach the token to GET. The exact override policy is a main ruling.

## Required focused tests before implementation is accepted

1. Hook route accepts a synthetic body above 1 KiB but below its finite cap; normal/control routes still reject above 1 KiB. Hook body above route cap gets 413. Header limit, connection/handler limits, exact Host, Origin rejection, and no CORS remain enforced.
2. Slow headers/body cannot outlive the hook's total deadline measured from accept; SessionStart provider wait never exceeds 1.5 seconds and total response is within 2 seconds. Prompt is cached-only and within 2 seconds. Exercise slow/no body, malformed JSON, and valid synthetic prompt payload without recording payload content.
3. Valid opaque IDs (including non-UUID) track independently; empty, missing, non-string, control-containing, and overbound IDs neither share history nor update it. Test first-prompt baseline suppression, a genuine worsening, unchanged-status suppression, improvement then later worsening, disappeared/reappeared buckets per the main ruling, 24-hour idle expiration and 1,024-entry LRU eviction. Verify only severity metadata is held.
4. SessionStart/CLI human text uses the same formatter and handles unknown, stale, unavailable, percentages, balances, counts and reset times. CLI `--json` remains raw v1 GET output. CLI uses GET `/quotas` only, never invokes providers or reads runtime lock state; enable/disable uses existing PUT and token header only after loopback URL validation.
5. Pi footer remains compact with stale/error states, Pi fetch timeout remains 8 seconds, and tests exercise the changed displayed output. Shell tests cover `QUOTA_FEED`, JSON passthrough, safe network errors, token non-disclosure and non-loopback control URL rejection. No test performs a real quota call.
