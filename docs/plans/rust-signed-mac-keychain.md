# Plan: signed native macOS Keychain support

The [write-proof ruling](rust-native-write-proof-ruling.md) supersedes the original raw write-denial assumption. Its [primary-source analysis](../research/rust-native-keychain-write-semantics.md) explains why read authorization does not establish an independent item-write permission. This plan includes that correction below; the initial verifier history remains recorded.

Goal: make the Rust daemon work independently on macOS and Linux by reading Cursor, Muse and Claude Code credentials through native Keychain APIs, while keeping Keychain interaction disabled inside the daemon. Linux stays file-only. Its existing behavior is preserved except for the explicitly approved shared credential-directory no-follow hardening. This plan authorizes no implementation, native Keychain call, signing, service operation, Git mutation or provider request.

## Rulings

1. **Runtime Keychain UI stays disabled.** The existing checked process-lifetime `SecKeychainSetUserInteractionAllowed(false)` guard runs before any query or mutation. Every ordinary provider test injects a fake store; none calls even the real suppression setter. A denied read/write returns a safe error. Never re-enable UI, retry with UI, spawn `/usr/bin/security`, or weaken policy from daemon code.
2. **Signing gives a stable code identity but not access by itself.** In the later signing step, use the inventoried Developer ID identity and verify the same designated requirement after every build/copy/update. No signing operation occurs in this implementation plan. An interactive keychain prompt required to authorize the signing key is a separate, owner-approved setup action, not permission for runtime dialogs.
3. **Owner ACL setup is explicit and app-specific.** The daemon never writes access lists. Before actual provider acceptance, the owner may use a supported Keychain UI to authorize only the signed foreground acceptance executable and later the installed signed executable for the exact required records. Never select “allow all applications.” If the UI cannot preserve signer-stable authorization, stop and request a new decision; do not use undocumented ACL blobs, arbitrary trust-list changes, or private APIs. Existing counts do not identify which applications are authorized.
4. **Claude service and account are fixed by contract.** Query only service `Claude Code-credentials`. Derive the account lazily at probe time from the effective OS user via `libc::getpwuid_r(geteuid())`; accept only a bounded (at most 64 KiB) result that is valid UTF-8, non-empty and contains no control characters. Do not use `$HOME` basename, `USER`, caller input, service-only secret lookup, fallback accounts or enumeration. Add an injectable fake OS-account lookup for ordinary tests; missing/invalid lookup returns an existing safe error and never logs the account. Before any owner-secret read, perform a separate owner-present no-secret metadata lookup for exactly that service and derived account, with both password output pointers NULL. If it does not match, fail closed without enumerating or trying another account. Cursor and Muse retain their existing exact service/account pairs.
5. **File precedence and fallback are explicit.** Valid Claude file credentials remain first. On macOS, fall back to Keychain only if the credential file is absent (`CredentialFileError::Missing`) or is safely read but unusable JSON/credential data (malformed JSON, missing `claudeAiOauth`/access token, empty or invalid access token). Do not fall back after unsafe path/file, symlink, non-regular file, insecure permissions, oversized content, unreadable I/O, invalid HOME/path or other boundary error; return the existing safe error. Linux keeps its current file-only behavior. Add a typed classification helper to `daemon/src/providers/credential_file.rs` only if needed; never parse error text.
6. **Claude renewal coherence is best effort, not CAS.** Legacy `SecKeychainItemModifyAttributesAndData` updates an existing item and has no demonstrated compare-and-swap with Claude Code. Re-read immediately before modify and refuse stale output if the item has changed; preserve unrelated JSON and never create/upsert a missing item. A narrow race remains between compare and modify, consistent with the migration plan's documented residual races. After modify, reload the entire actual item record. If Claude Code replaced it with another valid record, that complete reloaded record wins for the usage request. If read-back fails or is malformed, return a safe error; do not retry a stale write or roll back. This does not claim atomicity.
7. **Foreground acceptance precedes managed install without occupying its paths.** Build and sign the foreground acceptance binary at `$HOME/Library/Application Support/QuotaBar/acceptance/quotabard` in a 0700 acceptance directory; binary mode 0755. Use the same bundle identifier/designated requirement `com.aakshintala.quotabard` and Developer ID identity intended for release. Do not create or prepopulate the managed `.../bin/quotabard` destination. Later the normal no-clobber installer copies the signed bytes; re-verify the installed signature and repeat owner authorization/access checks at the installed path. Do not assume foreground authorization survives a path change. No force/adopt behavior is added.
8. **Swift and consumer removal is last.** Keep Swift source and targets until Mac and Linux services, Pi behavior, installed SessionStart hook behavior and rollback all pass. There is no installed QuotaBar UserPromptSubmit hook in the inspected inventory. Do not add one as part of migrating the existing hook; a new prompt hook is a separate product/config decision.

## Interfaces and invariants

- Keep `CredentialReader::read(KeychainTarget) -> Result<SecretBytes, KeychainReadError>` for Cursor/Muse. Claude's native operation is separately private and has no caller-supplied arbitrary service/account. Its account comes only from the injected OS-account resolver, then is validated inside the private native boundary.
- Production Claude probe construction chooses the platform store without I/O. Ordinary tests must inject fakes even for missing/malformed files; a negative test proves those cases cannot invoke a production native operation. The loopback test constructor also requires the fake store/account seam.
- Account resolution is lazy, effective-UID-based, bounded to 64 KiB and validated UTF-8/non-empty/control-free. Its failure maps to an existing safe error. Do not log its value.
- `Claude Code-credentials` plus the resolved account is the only Claude lookup. Owner setup first verifies that exact pair with both password outputs NULL. A mismatch blocks; no service-only search or alternate-account retry.
- File fallback occurs only for absent file or safely read but unusable JSON/credential content. Unsafe, oversized, unreadable and invalid-path outcomes stay errors. Linux remains file-only.
- All native calls follow process-lifetime interaction suppression. The native write operates on the found existing item reference only and changes data only; it does not create, delete, replace, or change ACL/attributes.
- Before modify, re-read and compare with the snapshot used for refresh. If different, parse/use the complete current record or fail without writing. After modify, reload and use that complete actual record, including a concurrent valid replacement. Read-back failure/malformed data is safe failure with no stale retry or rollback. Document the remaining compare/modify race.
- Keep OAuth JSON fields not owned by the refresh operation. Never log/serialize secrets to diagnostics/feed. Clear temporary owned byte buffers where supported by existing secret containers.
- Installer destination remains absent until the later service-install phase. Foreground acceptance binary is outside managed paths. Later installed-path signing/access acceptance is repeated rather than assumed.
